# opendirectoryd

The account services of pearOS, wire compatible with the `opendirectoryd` of macOS 26.7.2: Apple's libsystem_info (Libinfo's `ds` module and the membership API) gets the replies the Mac gives, so `getpwuid`, `getpwnam`, `getgrgid`, `getgrnam`, `getgrouplist`/`initgroups`, `getpwent`/`getgrent` and `mbr_uid_to_uuid`, `mbr_uuid_to_id`, `mbr_check_membership`, `mbr_check_service_membership` ... of a Mac program answer with the accounts of the system instead of waiting for a service that is not there (the real Dock looks it up 28 times at start).  Plain C, no Apple header; built on FreeBSD with clang + ld64.lld like `tccd`.  The protocol and the evidence: `research/docs/OPENDIRECTORY-DISTNOTED-WIRE.md`.

- Services: `com.apple.system.opendirectoryd.libinfo` and `com.apple.system.opendirectoryd.membership` (xpc pipes: "rpc_name", "rpc_version" 2 and the keys of the call; the reply carries "rpc_version" 2 and Apple's keys).  It must run as root: libinfo drops a reply whose audit token is not uid 0.
- Accounts: `/etc/passwd` and `/etc/group` (FreeBSD's files, plain file I/O); `/etc/master.passwd` only tells whether an account has a password (`pw_passwd` "********" then, "*" otherwise, as the Mac).  Single look-ups carry ints and `pw_uuid`/`gr_uuid`; the `getpwent`/`getgrent` lists carry the ids as strings and no uuid (the Mac's shapes).
- UUIDs (the files have no GeneratedUID): a user is `FFFFEEEE-DDDD-CCCC-BBBB-AAAA<uid>`, a group of `/etc/group` `ABCDEFAB-CDEF-ABCD-EFAB-CDEF<gid>` (what macOS stores for its own accounts: root, daemon, nobody, wheel, staff, admin ...); a gid that is in no file gets `AAAABBBB-CCCC-DDDD-EEEE-FFFF<gid>`, an unknown uid `FFFFEEEE-...<uid>` (opendirectoryd's answers).
- Membership: the user's primary group or a group that lists him; no nested groups (the Mac also puts every local user in `everyone` and `localaccounts`, which the FreeBSD files do not have).  `mbr_check_service_membership(user, S)`: the group `com.apple.access_S`, error 2 when it does not exist.
- Errors: "record not found" = error 2, a missing or mistyped key = error 22, as the Mac.  A call that opendirectoryd does not serve (hosts, services, protocols by key, an unknown rpc_name) gets no reply: the request is released, its reply right dies and the client's `xpc_pipe_routine` returns EIO (5) at once, which is what the Mac does.  The other `*ent` lists get the Mac's empty reply.
- `opendirectoryd -v` logs every request; `libinfo=NAME membership=NAME passwd=PATH group=PATH master=PATH` serve other names / files (tests on a Mac).
- Job for the launchd of d: `launchd/com.apple.opendirectoryd.plist` (`/usr/libexec/pearos/opendirectoryd`, started at the first look-up).

Build: `sh build.sh OUTDIR` (FreeBSD: llvm21; elsewhere `CC=clang LD64=ld64.lld sh build.sh OUTDIR`).

Tested on the Mac VM: Apple's libsystem_info against this daemon (job `com.pearos.t.od` as root, names redirected with `research/tools/opendirectory/odcap.dylib`, probes `odt` and `odraw` in the same folder) gives the Mac's reply shapes for every call above.  On the FreeBSD lab VM (darwinator): our launchd starts the job at the first look-up and the Mac's libsystem_info (dyld cache) gets the accounts of FreeBSD's files for getpwuid/getpwnam/getgrgid/getgrnam/getgrouplist/getpwent/getgrent and every mbr_* call of the probes.  The lab stacks of `d/session` still start `lsd-stub` with its own small libinfo part; do not give both the same name.
