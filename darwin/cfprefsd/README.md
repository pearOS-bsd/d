# cfprefsd

The preferences server of pearOS, wire compatible with the `cfprefsd` of macOS 26.7.2 (CoreFoundation-5026.6.7.5): CoreFoundation's `CFPreferences` and Foundation's `NSUserDefaults` of a Mac program read, write and observe their preferences through it as they do on the Mac, and the files are the Mac's (binary plists in `~/Library/Preferences`, `ByHost`, `/Library/Preferences`).  Plain C, no Apple header (`darwin.h` declares what it uses); built on FreeBSD or Linux with clang + ld64.lld against `libSystem.tbd` and `CoreFoundation.tbd` (CoreFoundation only for property lists and `CFHash`).  The protocol and the evidence: `research/docs/CFPREFSD-WIRE.md`; the probes and the recorded traffic of the Mac: `research/tools/cfprefsd`.

- `cfprefsd agent`: a user's instance, `com.apple.cfprefsd.agent` (job `launchd/com.apple.cfprefsd.xpc.agent.plist`, `@USER@` = the console user): the user's domains, shared memory `apple.cfprefs.<uid>v1`.  `cfprefsd daemon`: the system instance, `com.apple.cfprefsd.daemon` (job `launchd/com.apple.cfprefsd.xpc.daemon.plist`, root): `kCFPreferencesAnyUser` (`/Library/Preferences`), root and role accounts, managed preferences, shared memory `apple.cfprefs.daemonv1`.  Apple's takes the role from the launchd session and ignores the word; the job files pass the same word, so the result is the same.  The agent introduces itself to the daemon (op 2 with an endpoint) and again at `CFPreferencesAgentsShouldCheckIn`.
- Operations (`CFPreferencesOperation`): 1 read / write a source (`Key` + `Value`, `MultiKeySet`), 5 multi-message, 7 / 8 observe / stop, 9 the path, 4 flush a domain (a file written behind the server's back: `defaults delete`), 3 flush managed, 6 user deleted, 999 write everything now, 2 agent check-in.  Every reply of 1/7/8 has `CFPreferencesShmemName` / `Index` / `State`; the slot of a source is Apple's formula (`(CFHash(domain) % 585) * 7 + len % 7`, plus 0..6 for ByHost / user / AnyUser / managed / container): the indices match the Mac's for the same domains.
- What Apple does and this one does too: writes stay in memory and the slot is bumped at once; files are written by a 10 s timer, at once when the client asks (`CFPreferencesShouldWriteSynchronously`, what `defaults` and `CFPreferencesSynchronize` of a system user send), for a new file, at op 999 and at SIGTERM; a file is a binary plist written to `<file>.XXXXXXX`, fsync'd and renamed (mode 0600, 0644 for AnyUser; owner = the writer); a domain whose last key is removed stays as an empty dictionary; a missing directory is "Directory needed" (error type 4) and the client makes it (0700); another user's file needs read permission or an access token (an open file descriptor of it); a change is pushed to the other observers of the source (`{Domain, User, IsByHost, PID}`, one in flight per client, the others held); the current user's global domain mirrors `AppleLanguages` / `AppleLocale` with their `Sig_` keys into `.GlobalPreferences_m.plist` and returns it as `CFPreferencesValidationPropertyList`; the process quarantines itself as `com.apple.cfprefsd` like `/usr/sbin/cfprefsd`.
- A read is answered like Apple's: the file as last read or written (`CFPreferencesPropertyList`, or `PlistFD`, a descriptor of the file, when it is 1 MiB or more and the client does not ask `ValidatePlist`) and the changes not yet written on top of it (`PlistDiff` = `[key, value as the client sent it (null: removed), ...]`, cleared when the file is written).  The daemon writes at once when the user of the source is root or a role account (not for `kCFPreferencesAnyUser`).
- Not done (yet): cloud sources (`Domain not cloud-backed`), containers are taken as given (no sandbox look-up), no eviction of the cache, sandbox checks (pearOS has no sandbox).  Seen on the Mac: our files do not get the `com.apple.quarantine` xattr although the quarantine is applied without error (cause not found).
- `-v` logs every message, reply and notification on stderr.  `__CFPreferencesTestDaemon=1`: Apple's test mode, services `com.apple.cfprefsd.{agent,daemon}.test` and shared memory `test.cfprefs...`; Apple's clients use the same names when they have the variable, which is how this daemon is tested on a Mac next to Apple's.

Build: `sh build.sh OUTDIR` (FreeBSD: llvm21; elsewhere `CC=clang LD64=ld64.lld sh build.sh OUTDIR`; on a Mac `CC=clang MAC=1 sh build.sh OUTDIR`).  After adding a call: `sh gen-tbd.sh` (CI checks that the .tbd files are current).

Tested on the Mac VM (macOS 26.7.2, test mode, Apple's CoreFoundation / Foundation / `defaults` as clients, `research/tools/cfprefsd` probes run against Apple's daemon and ours and diffed after `norm.py`): the CFPreferences C API probe (read of a missing domain, set, synchronize, key list, ByHost, a global key, delete), `defaults write / read / delete`, the notification probe (`run2s`: two KVO callbacks), a pending change read by another process (the same file bytes and the same `PlistDiff`), a 1.2 MiB domain (`PlistFD`), the disk probe (file created at the first write, deferred rewrite through a new inode, mode, owner, empty dictionary after the last key) and the daemon probe (AnyUser written by root: 0644 root, read by a user; root's own domain: 0600) give the same messages, the same shared memory indices and the same files as Apple's; an NSUserDefaults suite observed by a second process gets the change notification and its KVO.  Apple's own agent replaced in a real session (GPU VM, SIP off, `research/tools/cfprefsd/swap.sh ours`: `user/501/com.apple.cfprefsd.xpc.agent` runs this binary): `defaults` writes and reads, the processes already running (Dock, Finder) reconnect, Calculator and TextEdit start, Calculator saves its preferences when it quits, Finder and SystemUIServer restart and draw, the Dock restarted after `defaults write com.apple.dock tilesize -int 32` comes up with the smaller tiles.
On the FreeBSD lab VM (darwinator, the Mac's dyld cache): our launchd starts both roles on demand (with our opendirectoryd for the accounts); the Mac's CoreFoundation runs the same C API probe to the end, gets "Directory needed", makes `~/Library/Preferences` and `ByHost` and the files are written (`ByHost/<domain>.<gethostuuid>.plist`); an observer gets the notification, answers it and reads the domain again (the KVO callback of the Foundation probe was not printed there: not investigated yet).
